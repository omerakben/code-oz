# Synthesis — Code-Oz vs maestro

## Outcome

**YES, with selective borrows. Comparison closed at the rule layer; one runtime sub-comparison (`code-oz watch`) deferred for demand-gated reopening.**

Codex's verdict was `fix-first`, not `push`. Three findings were grounded in code I verified after the debate:

## Decisions per borrow

### B1 — Wave-verification primitive  *(narrowed)*

**COMPARISON said:** VERIFY emits `WAVE_VERIFY.json` with grep recounts of every numeric claim in `BUILD_REPORT.md`.

**Codex finding:** BUILD_REPORT is mostly orchestrator-authored structured data, not a claim ledger. Grepping arbitrary prose for numbers is brittle. If BUILD_REPORT needs structured count rows, B1 becomes two surfaces (BUILD schema + VERIFY artifact) — a rule-20 violation. Also: the M16 C9 failure mode was authority bundling, not rename blindness. B1 helps only if it verifies task/file completeness.

**Synthesis decision:** Narrow B1 to "VERIFY derives completeness checks from existing PLAN task ids and BUILD task-completion events; emits `WAVE_VERIFY.json` cross-checking that every PLAN task id has a matching `task_completed` event with the declared file paths actually present in the worktree." No BUILD schema change. One rule-20 axis. Closes rule 5 against the *actual* M16 C9 failure mode (authority bundling = some tasks not finished but reported as done) rather than the maestro rename-blindness mode.

**Status:** Accepted, narrowed. Milestone hook: pair with whichever milestone next touches VERIFY. Stand-alone if it stays under one commit.

### B2 — Heartbeat schema  *(unchanged)*

**Codex agreed:** defer until consumer exists; document as a *projection* over `events.jsonl` and current-state, not a second source of truth.

**Synthesis decision:** Accepted as written. Specify in `docs/contracts/HEARTBEAT.md` (when written) that heartbeat is a derived view, not authoritative state. Single line: `{ runId, phase, lastEventTs, status }` computable from the latest event. No writer, no separate file, just the projection contract.

**Status:** Accepted, deferred. No milestone slot until a consumer arrives.

### B3 — `PLAN_DIFF.md`  *(deferred behind SHIP contract)*

**COMPARISON said:** Pair with whichever milestone next adds a Scientist-tail extension; one-commit add.

**Codex finding:** No `docs/contracts/SHIP.md` exists (verified). PLAN_DIFF is a SHIP-tail artifact, but there is no SHIP contract for the tail to attach to. Also: PLAN_DIFF should be deterministic-generated from PLAN task ids + BUILD_REPORT manifests + REVIEW/VERIFY outcomes, not human-curated. Calling it a "small commit" is premature.

**Synthesis decision:** B3 is now blocked on a `docs/contracts/SHIP.md` decision. The decision tree:

1. **If SHIP gets its own contract this year** → PLAN_DIFF.md is a SHIP-tail artifact, deterministically generated by a `ship.summarize-plan-diff` step that compares PLAN task ids and acceptance criteria against existing task/gate/review events (`task_completed`, `gate_written`, `verify_completed`, `review_resolved`, `review_panel_completed`). Scientist tail (rule 15) reads it to update HYPOTHESES/OPEN_QUESTIONS.
2. **If SHIP stays implicit** → fold the diff into the existing Scientist tail at REVIEW gate, scoped to PLAN-vs-REVIEW reconciliation only.

The synthesis recommends path 1 because shipping has been an authority-creep risk multiple times (M16 C9 was at SHIP-1). A real SHIP contract closes that gap.

**Status:** Accepted in principle, blocked on SHIP contract decision. Open question recorded in the comparison index.

### B4 — `NEXT_RUN.md` forward-feed  *(separated from B5)*

**Codex finding:** Forward-handoff artifact, not a terminal-state class. Different consumer, different risk profile than B5.

**Synthesis decision:** B4 stands alone. Contract: a SHIP-tail or REVIEW-tail artifact written when a run wants to seed the next DEFINE/AUDIT with positive-direction context. Optional, opt-in. Consumed by DEFINE/AUDIT only when explicitly wired through a future `.code-oz/config.yaml` option. Zero risk if unwired — it just sits there.

**Status:** Accepted, decoupled from B5. Could land as a one-commit add once SHIP contract decision is made (B4 is a SHIP-tail artifact for the same reason B3 is).

### B5 — `ABANDON.json` / `outcome=abandoned`  *(elevated to its own decision)*

**COMPARISON said:** "No risk I can see. Additive."

**Codex finding (verified against code):** `RUN_OUTCOMES` is `['shipped', 'stopped', 'paused']` at `src/state/schemas.ts:421`. Adding `abandoned` requires:

- `RUN_OUTCOMES` enum change in `schemas.ts`
- Validator update in `events.ts:418` (`run_ended.outcome` rule string)
- Emitter sites that conclude with `abandoned` (currently only `run.ts:1371,1503` emit `shipped`)
- Possibly current-state projection logic if "abandoned" runs need different rendering
- Possibly cleanup behavior if abandoned runs leave artifacts

**Synthesis decision:** B5 is its own milestone-class decision, not a freebie bundled with B4. The minimal version is `run_ended.outcome='abandoned' + reason: string` with no cleanup behavior — that is one schema axis (extending the enum) plus emitter sites. The cleanup-on-next-run side is explicitly out of scope.

The deeper question is: when *should* a code-oz run end abandoned? Maestro's ~10% abandonment rate comes from PR-gate blockers and DEFINE-finds-nothing scenarios. Code-oz has neither failure mode in-spine today. A DEFINE that finds nothing today produces an empty SPEC.md and proceeds — arguably wrong, but not currently observed as a problem. Without a use case, B5 is theoretical.

**Status:** Accepted as a *concept*, deferred until use case emerges. Recorded as an open question on the comparison index. Bundle with B4 *only* if reduced to enum-extension + reason, no cleanup, no auto-detection logic.

### B7 — Perpetual orchestrator loop / `code-oz watch`  *(rejection downgraded to deferral)*

**COMPARISON said:** Reject for v0.x. Rule 21's measurable-risk-reduction test not met.

**Codex finding:** Rule 21 is the *wrong primary rule*. A one-provider watch loop is not a parallel-provider surface. Rule 20 is the right primary lens (watch introduces a new runtime authority boundary). Also: W3-lite is one data point, not proof perpetual mode has no product value. Don't *finally* reject — defer.

**Synthesis decision:** Adopt Codex's framing. Reject maestro's bash perpetual loop (architectural fork) for v0.x. *Defer* `code-oz watch` as a sub-comparison reopened by future demand signal.

**Contract surface if reopened (Codex's draft, accepted):**
- Fresh `runId` per cycle. Reusing `runId` across cycles violates the append-only gate model.
- Separate `watchId` (or `cycleId`) for the perpetual session itself.
- Heartbeat is a derived projection of latest event, not a parallel state file.
- Cycle counter outside per-run gate files.
- No reuse of success gates across cycles. Each cycle is its own gate sequence.
- No external supervisors in v1. The supervisor surface is its own future authority.
- Halt conditions: `NEEDS_INTERVENTION`, `STOP` file, budget kill, foreign worktree drift.

**Status:** Maestro bash loop rejected. `code-oz watch` deferred with contract draft. Reopens on first credible demand signal (recurring unattended use case beyond W3-lite scope).

## Closing the W3-lite over-read

COMPARISON.md cited the W3-lite Ralph Loop as evidence that "thin shell wrapper is sufficient" for unattended overnight runs. Codex flagged this as over-reading. Synthesis correction: W3-lite was a 10-iteration / 1.5h scaffold under tight scope (hard caps, manual morning review) that proved thin wrappers can ship a known shape of work overnight. It does *not* prove perpetual mode has no product value at scale. The B7 deferral is grounded in "no current demand signal," not "thin wrappers are universal."

## Closing the rule-21 misapplication

COMPARISON.md applied rule 21 to B7. Rule 21 governs *parallel-provider* surfaces (Reviewer panels, parallel builders, multi-opponent debate, Researcher fan-out). A one-provider watch loop is not parallel-provider — it is a runtime authority boundary, which is rule 20's domain. Synthesis correction: rule 21 was a misapplication; rule 20 is the right primary lens for B7 and any future `code-oz watch` decision. This correction is recorded for the influence library so future template comparisons don't repeat the slip.
