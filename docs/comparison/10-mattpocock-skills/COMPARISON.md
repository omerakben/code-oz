## 1. What `mattpocock-skills` is

A 13-skill plugin (10 engineering + 3 productivity) plus 4 misc skills, distributed via [skills.sh](https://skills.sh) and consumed by Claude Code, Codex, or any harness that reads SKILL.md frontmatter. No runtime. No phase gates. No persona orchestration. The *user* drives every skill by hand.

| Layer | Count | Purpose |
|---|---|---|
| Engineering skills (`skills/engineering/<name>/SKILL.md`) | 10 | Daily code work — alignment, TDD, debugging, refactor, prototype, triage, issue/PRD authoring |
| Productivity skills (`skills/productivity/<name>/SKILL.md`) | 3 | `grill-me` (alignment, no codebase), `caveman` (~75% token compression), `write-a-skill` (meta) |
| Misc (`skills/misc/<name>/SKILL.md`) | 4 | git-guardrails, shoehorn migration, scaffold-exercises, pre-commit |
| Setup | 1 | `setup-matt-pocock-skills` — bootstraps `docs/agents/{issue-tracker,triage-labels,domain}.md` |
| Plugin manifest | 1 | `.claude-plugin/plugin.json` — registers the 13 advertised skills |
| Repo glue | 2 | `scripts/link-skills.sh`, `scripts/list-skills.sh` |

The product thesis sits at the top of the README:

> *Approaches like GSD, BMAD, and Spec-Kit try to help by owning the process. But while doing so, they take away your control and make bugs in the process hard to resolve. These skills are designed to be small, easy to adapt, and composable. They work with any model. Hack around with them. Make them your own.*

That paragraph is the philosophical opposite of code-oz. code-oz **explicitly owns the process** — phase gates, file-based signals, cross-family review, run-level budgets, multi-agent orchestration. So the comparison is structurally interesting: do code-oz's process locks earn their place against a polished anti-process pack?

### Three composition rules

The template enforces a small surface area:

- **Skills are the *how*.** No personas, no `/commands`, no orchestrator.
- **The user is the orchestrator.** Skills do not invoke other skills (with one exception: `triage` invokes `grill-with-docs` when an issue needs grilling).
- **Skills are composable, not assembled.** The user picks which skill to run when.

### The flagship: `grill-with-docs`

Matt explicitly calls this *"the single coolest technique in this repo. Try it, and see."* The mechanic:

1. Interview the user one question at a time.
2. When the user uses a vague or overloaded term, propose a precise canonical term.
3. Cross-reference proposed terminology against existing code.
4. **Update `CONTEXT.md` *inline*** — capture terms as they resolve, not in a batch.
5. Offer ADRs sparingly, only when **all three** are true: hard to reverse + surprising without context + result of a real trade-off.

The byproduct is a project-level domain glossary that subsequent skills (`tdd`, `diagnose`, `triage`, `to-issues`, `to-prd`, `improve-codebase-architecture`) consume so test names, issue titles, refactor proposals, and PRD prose all use *the same vocabulary the developer uses with their domain experts*.

### The other ten skills

| Skill | Mechanism | Notable discipline |
|---|---|---|
| `tdd` | red-green-refactor with **vertical slicing** as the explicit anti-horizontal-slicing rule | "Tests in bulk test imagined behavior, not actual behavior" |
| `diagnose` | 6-phase debugging discipline | **Phase 1 = "Build a feedback loop" is *the* skill**; everything else is mechanical |
| `triage` | issue-tracker state machine (5 state roles + 2 category roles) | Every triage comment prefixed `> *This was generated by AI during triage.*` |
| `to-issues` | break a plan into **tracer-bullet vertical slices** | HITL/AFK split, dependency ordering, no file paths in issue body |
| `to-prd` | PRD synthesis from current conversation context | "Do NOT interview the user — synthesize what you already know" |
| `improve-codebase-architecture` | Ousterhout deep-modules, **deletion test**, adapter rule (1=hypothetical, 2=real) | Dedicated `LANGUAGE.md` glossary for **architecture vocabulary** (Module, Interface, Implementation, Depth, Seam, Adapter, Leverage, Locality) |
| `prototype` | throwaway code with two branches: logic (terminal app) vs UI (variants on one route) | "Throwaway from day one, and clearly marked as such" |
| `zoom-out` | minimal — "go up a layer of abstraction" | 7 lines total; `disable-model-invocation: true` (only fires when the user asks) |
| `setup-matt-pocock-skills` | bootstraps `docs/agents/*.md` for the per-repo config the other skills assume | One section at a time, never all three at once |
| `grill-me` | the no-codebase variant of `grill-with-docs` | 10 lines |
| `caveman` | ~75% token-compression mode | Drops articles, fillers, pleasantries; arrows for causality; auto-clarity exception for security warnings |
| `write-a-skill` | meta-skill for skill authoring | "Description is the only thing your agent sees when deciding which skill to load" |

## 2. What code-oz is (the snapshot for this comparison)

A standalone Bun + TypeScript CLI runtime with:

- **Phase taxonomy** (greenfield: DEFINE → PLAN → BUILD → VERIFY → REVIEW → SHIP; brownfield: AUDIT → PLAN → BUILD → VERIFY → REVIEW → SHIP)
- **File-based gates** (`state/GATE_<PHASE>_PASSED.json` schema-validated, never parsed from LLM text — rule 1)
- **Plain-Markdown artifact contracts** (`SPEC.md`, `PLAN.md`, `SOURCE_CHECK.md`, `BUILD_REPORT.md`, `VERIFY.md`, `REVIEW.md`, `AUDIT.md`)
- **Universal anti-slop rules** in `src/prompts/universal-rules.md` (10 prohibitions + 10 affirmations) imported by every persona prompt — rule 16
- **Maestro discipline** (rule-checker role, 9-family bug map, 4-layer file-system memory) — rule 17
- **REPO_CONTEXT permission scope** (`tool_use.repo_context`, audited via `repo_context_searched` events) — rule 18
- **Run-level budget enforcement** (`budgets.global` cumulative caps + per-role policy from M13) — rule 19
- **One authority boundary per milestone** — rule 20
- **No new parallel-provider surface without measurable risk reduction** — rule 21
- **Scientist tails** at every phase (`HYPOTHESES.md`, `OPEN_QUESTIONS.md`) — rule 15
- **Cross-family review** at REVIEW (a different provider family from BUILD) — rule 2
- **3-source verification** before any code lands (spec + reference code + library docs) — rule 3
- **`requestDebate()` runtime primitive** (M10, single-opponent only) — rule 20
- **Reviewer panel v1** (M14, first simultaneous-provider surface)
- **Debate-policy scheduler v1** (M15)
- **Production CLI** (M16, 12 production bugs caught and closed by C12 e2e + Codex R1)
- **Multi-provider runtime** with capability contract (M11), company roster (M12), role-cost policy (M13), xAI direct provider (PE-1)

The product north star (`docs/product/AI_SOFTWARE_COMPANY_THESIS.md`): *"`code-oz` is a repo-native agentic SDLC runtime (market category) framed as an AI software company (product metaphor)."* Provider and model bias are real; the product coordinates role-specialized agents through artifacts, evidence gates, debate, verification, and cross-family review instead of trusting one model's confidence.

## 4. Where code-oz structurally exceeds `mattpocock-skills`

Twelve material gaps where code-oz's surface dominates the template's. Listed because the influence library tracks both directions.

1. **File-based gate signals** (rule 1) — Matt's skills produce Markdown artifacts but have no machine-readable pass/fail signal between skills. The user gates by hand.
2. **Cross-family REVIEW** (rule 2) — `improve-codebase-architecture` is run by the same model that wrote the code. No cross-family review surface.
3. **3-source verification** (rule 3) — `tdd` Planning step and `diagnose` Phase 1 reach for documentation but no formal `SOURCE_CHECK.md` gate.
4. **Scientist tails everywhere** (rule 15) — `diagnose` enforces hypotheses + open questions; the other skills do not. code-oz enforces them at every phase.
5. **Universal anti-slop rules in every persona prompt** (rule 16) — Matt's skills are individually well-written but do not import a universal rule sheet. Each is a standalone Markdown file.
6. **Maestro discipline + 9-family bug map** (rule 17) — no equivalent.
7. **REPO_CONTEXT permission scope** (rule 18) — `improve-codebase-architecture` uses an Explore subagent but with no audited permission scope or `repo_context_searched` events.
8. **Run-level budget enforcement** (rule 19) — no budget primitive at all; this is *user-driven*, the user pays for tokens by stopping the session.
9. **One authority boundary per milestone** (rule 20) — Matt's skills *are* small and composable, which is the same principle. But code-oz codifies it as a development-process invariant; Matt's pack manifests it organically without a stated rule.
10. **No new parallel-provider surface without measurable risk reduction** (rule 21) — Matt's skills are single-provider by construction; the rule is implicit. code-oz's panel + debate features earn this rule explicitly.
11. **`requestDebate()` runtime primitive** (M10) — no debate surface in Matt's pack.
12. **Provider capability contract / role-cost policy / company roster** (M11/M12/M13) — multi-provider runtime is out-of-scope for Matt's pack.

## 5. Verdict: **YES, with selective borrows**

code-oz already meets the bar this template sets and exceeds it on 12 dimensions. The borrow set is concentrated in **vocabulary discipline** (project-level glossary, deep-modules language) and **operational discipline** (diagnose Phase-1 feedback-loop primacy, 3-true ADR gate, tagged-and-grepped instrumentation).

### Ranked borrow set

Six candidates, ranked. Codex will challenge the rankings, the count, and whether any belong in v0.17 or should defer to v0.2.

#### B1 — Project glossary as a phase artifact (`CONTEXT.md` equivalent) — STRONG

**The pattern.** During DEFINE, the Definer maintains a project-level domain glossary that subsequent persona prompts read so vocabulary stays consistent across SPEC.md, PLAN.md, BUILD_REPORT.md, etc. Updated *inline* during the DEFINE interview, not in a batch. Format from `CONTEXT-FORMAT.md`: bold term, one-sentence definition, `_Avoid_:` aliases, relationships, example dialogue, flagged ambiguities.

**Why it earns a place at v0.17.** Rule 16 prohibits "elegant variation" / "synonym cycling" but provides no shared vocabulary file. Personas drift terminology because they have nowhere to anchor. The universal anti-slop rule sheet is a *prohibition* without a *positive surface*; the project glossary is the missing positive surface.

**Where it lands.** A new artifact `state/GLOSSARY.md` (or `state/CONTEXT.md`) produced by DEFINE, validated by a lightweight schema (term, definition, avoid-list). Subsequent personas receive it in `ProviderRequest.files`. Updates are append-only during DEFINE and resolved during PLAN's SOURCE_CHECK pass.

**Authority cost.** New artifact, but it lives inside DEFINE — no new phase or gate. Rule 20 budget impact: zero new authority boundaries; one new artifact slot. Suggest M17 candidate (alongside M16 closure) or fold into M14.1 (reviewer-isolation) prep work.

**Risk.** Schema scope creep. Mitigated by limiting v1 to: term, one-sentence definition, avoid-aliases. No relationships, no example dialogues in v1.

#### B2 — VERIFY's Phase-1-as-the-skill rule (feedback-loop primacy) — STRONG

**The pattern.** Matt's `diagnose` skill: *"Phase 1 — Build a feedback loop. **This is the skill.** Everything else is mechanical."* He enumerates 10 ways to construct one (failing test → curl/HTTP → CLI fixture → Playwright → trace replay → throwaway harness → property/fuzz → bisection → differential → HITL bash). Then iterates on the loop itself: faster, sharper signal, more deterministic.

**Why it earns a place at v0.17.** code-oz's VERIFY persona prompt does not enshrine "feedback loop construction is the skill itself." VERIFY produces a `VERIFY.md` artifact but the persona is implicitly trusted to find the right verification surface. Without the explicit rule, VERIFY can drift into "stare at the code" mode — exactly the failure Matt warns against.

**Where it lands.** Edit to VERIFY persona prompt and to the universal-rules.md affirmations: *"Build a feedback loop before forming hypotheses. The loop is the skill."* Plus the 10-ways-to-construct list as a reference appendix. No new artifact, no new gate.

**Authority cost.** Zero. Persona prompt edit only.

**Risk.** Verbose persona prompts hurt token budgets. Mitigated by referencing the 10-ways list in `references/diagnose-loops.md` rather than inlining.

#### B3 — Deep-modules architecture vocabulary in REVIEW persona — MEDIUM

**The pattern.** Matt's `improve-codebase-architecture/LANGUAGE.md` defines 8 architecture terms (Module, Interface, Implementation, Depth, Seam, Adapter, Leverage, Locality) plus the deletion test, the "1 adapter hypothetical / 2 adapter real" rule, and "the interface is the test surface."

**Why it earns a place at v0.17.** REVIEW persona has universal anti-slop rules but no shared *architecture* vocabulary. REVIEW findings drift into "this should be refactored" / "extract this" without a precise term for *what* is being suggested. The deep-modules vocabulary is opinionated, narrow, and rejects DDD overload (e.g., "boundary" → "seam") — which fits code-oz's universal-rules style.

**Where it lands.** Edit to REVIEW persona prompt: import an `ARCHITECTURE_LANGUAGE.md` reference (analogue to `universal-rules.md`). REVIEW findings cite Module/Interface/Seam vocabulary instead of generic "refactor" terms. PR comments and follow-ups can reference the same vocabulary.

**Authority cost.** Zero. Persona prompt + reference file.

**Risk.** Vocabulary lock-in. Mitigated by (a) keeping it scoped to REVIEW only in v1 and (b) marking it as a guideline, not a hard rule.

#### B4 — 3-true ADR gate for the project under construction — MEDIUM

**The pattern.** Matt's `grill-with-docs`: *"Only offer to create an ADR when **all three** are true: hard to reverse + surprising without context + result of a real trade-off."*

**Why it earns a place at v0.17.** code-oz uses ADRs internally (`docs/adr/0001-mvp-option-e.md`) but has no rule about *when* the orchestrator should produce an ADR for the project under construction. PLAN can drift into "write an ADR for every decision" or "no ADRs at all." The 3-true gate is a precise discriminator.

**Where it lands.** Edit to PLAN persona prompt and SOURCE_CHECK contract: *"Offer an ADR only when all three are true: hard to reverse + surprising without context + result of a real trade-off. Otherwise, capture the decision in PLAN.md prose."* Plus a reference appendix `references/adr-gate.md` with examples.

**Authority cost.** Zero. Persona prompt edit only.

**Risk.** PLAN persona may under-produce ADRs. Mitigated by listing the gate as an affordance, not a default-off. Acceptable failure mode: under-production is recoverable; over-production rots.

#### B5 — Tagged-and-grepped debug instrumentation in VERIFY — SMALL

**The pattern.** Matt's `diagnose` Phase 4: *"Tag every debug log with a unique prefix, e.g. `[DEBUG-a4f2]`. Cleanup at the end becomes a single grep. Untagged logs survive; tagged logs die."*

**Why it earns a place at v0.17.** Code-oz's BUILD agents may add diagnostic instrumentation that survives into the artifact. No discipline for cleanup. The tagged-prefix discipline gives VERIFY a deterministic cleanup surface (`grep DEBUG-` at end of phase).

**Where it lands.** Edit to BUILD and VERIFY persona prompts: *"Diagnostic instrumentation must use the prefix `[DEBUG-<runId-shortcut>]`. VERIFY cleanup runs `grep -r 'DEBUG-' src/` as the last step before writing GATE_VERIFY_PASSED.json."* Universal-rules.md affirmation.

**Authority cost.** Zero. Persona prompt edit.

**Risk.** False positives in unrelated codebases that already use `DEBUG`. Mitigated by the runId-shortcut suffix.

#### B6 — Provenance prefix on AUDIT findings — SMALL

**The pattern.** Matt's `triage`: *"Every comment or issue posted to the issue tracker during triage must start with `> *This was generated by AI during triage.*`"*

**Why it earns a place at v0.17.** code-oz's AUDIT.md (brownfield) is clearly AI-generated by context but no provenance prefix is enforced. When AUDIT findings get copy-pasted into GitHub issues by the user, the AI provenance is lost. A standardized prefix preserves it.

**Where it lands.** AUDIT artifact contract update: *"Each finding bullet MUST be prefixed `> *AUDIT-<runId>:*` so downstream issue tracker copy-paste preserves provenance."*

**Authority cost.** Zero. Artifact contract edit.

**Risk.** None material.

## 6. Open questions for Codex

The Codex debate must challenge:

1. **Is B1 (`CONTEXT.md` glossary) a v0.17 borrow or a v0.2 deferral?** It introduces a new artifact slot during DEFINE. Rule 20 says one authority boundary per milestone; does this count as a new boundary or as an artifact extension within DEFINE's existing boundary?

2. **Is B2 (VERIFY Phase-1-as-the-skill) a persona-prompt edit or a contract change?** I argued zero authority cost, but if VERIFY's contract changes shape because the feedback-loop is now mandatory before VERIFY.md is produced, that *is* a contract change.

3. **Is B3 (deep-modules vocabulary) over-reaching at v0.17?** REVIEW already runs cross-family. Adding vocabulary lock-in might constrain reviewer panel models inconsistently across families. Should this defer until M14.1 reviewer-isolation lands?

4. **Are we right to reject `caveman` (N2) outright?** Or should we run a measured experiment first (M13 budgets give us the cost telemetry) before deciding?

5. **Is the rejection of `triage` (N5) correct?** AUDIT findings could benefit from a 5-state classification more than I credited. Worth a measured POC?

6. **Do the borrows together count as more than one authority boundary at v0.17?** If yes, which ones must defer to M18+?

7. **Is the `LANGUAGE.md`-style architecture vocabulary the right import shape for REVIEW?** Or should it be inline in the persona prompt?

## 7. Summary

- **Verdict:** **YES, with selective borrows.**
- **Borrow count:** 6 ranked candidates (B1, B2 strong; B3, B4 medium; B5, B6 small) + 7 explicit no-borrows.
- **code-oz exceeds** the template on 12 dimensions; the gap is in vocabulary discipline + operational discipline, not architecture.
- **Authority budget:** 4 of the 6 borrows are persona-prompt edits (B2, B3, B4, B5). B1 introduces a new artifact slot inside DEFINE. B6 is an artifact contract edit. **Net: 1 new artifact, 4 prompt edits, 1 contract edit** — well within rule 20's "one new authority per milestone" envelope if framed as a single milestone.
- **Suggested milestone target:** M17 (vocabulary + operational discipline pass) bundling B1 + B2 + B3 + B4 + B5 + B6 if Codex agrees they fit one authority boundary; otherwise split B1 (artifact) from B2-B6 (prompts/contracts) across two milestones.
- **Prior context:** the M14.1 reviewer-isolation candidate from `03-aris/SYNTHESIS.md` and the M17-M20 reviewer-memory sequence from `01-ace/SYNTHESIS.md` are the relevant adjacent milestones; B3 may interlock with M14.1.
