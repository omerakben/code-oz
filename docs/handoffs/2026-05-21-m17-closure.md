## What shipped

M17 builds the brownfield AUDIT runtime — the brownfield analog of DEFINE + SPEC + Lead-SPEC-read.

After M17, `code-oz run` on a brownfield repo:

1. Routes via `dispatchAudit` (fresh-run profile check + active-run dispatch branch in `src/commands/run.ts`)
2. `runAudit` invokes the `auditor` persona via `composeAuditPrompt` (universal-rules injected at composition time per rule 16)
3. Persists `AUDIT.md` (schema-validated by `src/artifacts/audit-schema.ts` + `audit-parser.ts`)
4. Emits `audit_completed` with `auditReportSha256`
5. Calls `runScientistPhaseTail` — writes `HYPOTHESES.md` + `OPEN_QUESTIONS.md`
6. Emits `gate_required(audit)`
7. `code-oz approve audit` runs `preApproveAuditHook` (sha-binding against `audit_completed` event + `validateAuditMarkdown` + `validateScientistSidecars`), then calls the generic `approveGate()` — no new gate authority introduced (rule 20, rule 1)
8. `runPlan` (brownfield) reads `AUDIT.md` instead of `SPEC.md` (profile source is event-derived run state per rule 1, NOT mutable config); Lead persona has an inline brownfield section; SOURCE_CHECK grammar extends to `SC-AUDIT-NNN`; brownfield SOURCE_CHECK uses `## Audit sources` replacing `## Spec sources`

Greenfield DEFINE → PLAN → BUILD → VERIFY → REVIEW → SHIP is completely unchanged.

## Two e2e-caught bugs (why they slipped per-commit review)

Both bugs were present in code that passed per-commit Codex seam reviews and all fixture-level unit tests. They only surfaced when C8 ran the full brownfield lifecycle end-to-end through the spawned CLI binary.

**Bug A — un-stripped AUDIT ready-signal.**
`composeAuditPrompt` constructed the system prompt using the same `READY_SIGNAL` substitution token as other composers, but the audit-system template did not strip it correctly from the assembled text. The auditor persona body received the ready-signal token as literal text, and the `audit_completed` event fired with a corrupted artifact body. Per-commit fixture tests passed because they verified individual prompt-composition steps, not the full pipeline through `runAudit` → event emission → artifact persistence. The seam review on C4-machinery focused on the composition-time universal-rules test and the CI leak guard, not on the downstream artifact surface.

**Bug B — Scientist phase-tail never wired.**
`runAudit` in C3-C7 did not call `runScientistPhaseTail`. The Scientist phase-tail contract (`docs/contracts/SCIENTIST.md`) requires every phase that produces a primary artifact to call it before `gate_required`. Per-commit reviews on C3 and subsequent commits reviewed the event sequence as documented, and the kickoff's event table listed `artifact_recorded(AUDIT.md)` and `audit_completed` but did not list `runScientistPhaseTail` explicitly. The `validateScientistSidecars` call inside `preApproveAuditHook` (C6) would have blocked every `code-oz approve audit` invocation in production. This is the same class of coupling bug that M16's C8/C9 surfaced: a cross-phase contract (Scientist tail) whose enforcement lives in the approve hook, not in the phase itself, only shows up when the full approve path runs.

Both bugs are empirical evidence for rule 19 (milestone-level e2e is non-negotiable for state-machine and cross-phase work) and for rule 20 applied carefully: even a single authority boundary can span multiple surfaces that only couple at runtime.

### Live brownfield smoke: skipped

The kickoff (`docs/design/SESSION_M17_KICKOFF.md` line 41) made live brownfield smoke OPTIONAL: "if skipped before tag, closure note documents why." It was skipped because M17 built and ran autonomously without live-provider credentials or budget invoked. The R1 impl packet asks Codex to evaluate whether the FakeProvider e2e constitutes adequate coverage or whether a live smoke run is required before the tag.

### Two `SOURCE_ID_PATTERN` copies

`src/artifacts/source-check.ts` and `src/artifacts/plan.ts` each hold a copy of `SOURCE_ID_PATTERN`, both extended with the `AUDIT` arm in C7. Codex's C7 seam review ruled this acceptable-with-note (both copies are in sync and covered by tests). Extract a single shared exported grammar on the next artifact-contract touch to prevent drift.

### Stale kickoff event names

`docs/design/SESSION_M17_KICKOFF.md` (C3 row, approximately line 82) and `docs/research/CODEX_BRIEFING_M17.md` (approximately line 124) anticipated events `artifact_recorded(AUDIT.md)` and `persona_invocation_started/_completed(auditor)` that were never implemented. The engine uses the existing vocabulary `agent_invoked` / `agent_completed` plus the new `audit_completed` sha event (mirroring `build_completed`). Adding `artifact_recorded` or distinct persona lifecycle events for AUDIT would be a new event-vocabulary surface; that is a rule-20 authority change out of M17 scope. The implementation intentionally chose the existing event set. No action required before tag; the divergence is a doc-only artifact.

### Auditor not in `M12_COMPANY_ROLES`

The auditor persona was introduced in M17, after the company roster was locked in M12. It does not appear in `M12_COMPANY_ROLES`, so no per-role budget gating applies to the auditor. Global and per-phase budgets (rule 19) still apply. Adding the auditor to the role roster is a separate rule-20 authority change. Defer to the next planning round that touches `M12_COMPANY_ROLES`.

### Lead.md leak-guard coverage gap

The rule-16 CI grep guard introduced in C4-machinery targets the `auditor` persona body sentinel (`AUDITOR_PERSONA_BODY_BEGIN`). The `lead.md` brownfield section added in C4-prose and C7 is also rule-16 prose (hand-authored by Ozzy + Claude, not generated). The guard does not currently cover `lead.md`. Extending it to cover the lead persona brownfield section is a small follow-up.
