## Five new findings (v0.20.3 candidates)

These all surfaced inside ~12 minutes of real first-friend interaction. None block v0.20.2; all matter for the friend experience:

### #1 Brownfield detector treats `INTENT.md` as user content

`code-oz init` on a directory containing `git init` + `INTENT.md` + no other files classifies the project as **brownfield**, sets `profile: brownfield` in config.yaml. INTENT.md is supposed to be the greenfield seed marker — the detector should ignore it.

**Symptom for friends:** AUDIT phase fires; no AUDIT runtime exists (deferred to v0.21); orchestrator emits DEFINE-style work via the audit phase entry; gate becomes unreachable because `code-oz approve audit` fails ("no agent registered for phase 'audit'") and `code-oz approve define` fails ("current phase is 'audit'"). Stuck. The workaround is to delete `.code-oz/`, move INTENT.md aside, re-init, move INTENT.md back.

**Fix:** make `INTENT.md` an explicit greenfield-seed marker in `src/policy/profile-detector.ts`.

### #2 BUILD requires git HEAD; no graceful empty-repo handling

`git init` + write `INTENT.md` (with no `git commit`) breaks BUILD with `worktree_base_head_unknown` and a raw git error: `fatal: ambiguous argument 'HEAD': unknown revision or path not in the working tree.`

**Symptom for friends:** "code-oz seems to break on git stuff" mystery. The intervention message exposes a raw git error string instead of saying "your project's git repository has no commits — run `git commit --allow-empty -m 'init'` before retrying."

**Fix:** in the worktree resolver (`src/worktree/load-or-create-run-worktree.ts`), detect empty repo and emit a friendly intervention with the exact remedy command.

### #3 BUILD validator's 200-char Notes cap surfaces cryptically

Builder's response for quizr T-001 had a Notes bullet exceeding 200 characters (from the protocol locked in `build-system.md`). Orchestrator correctly emitted `build_report_notes_too_long` intervention. But the message to the operator is "Notes bullet exceeds 200 characters" with no example, no fix-it command, no hint that this is a builder-prompt-discipline issue.

**Symptom for friends:** "code-oz says my Notes are too long but I didn't write them." The Notes came from the model.

**Fix:** intervention payload should include (a) which bullet exceeded, (b) the actual character count, (c) the action: rerun BUILD and the orchestrator will inject a "keep Notes ≤ 200 chars" reminder for attempt 2 (carry-forward).

### #4 GUI doesn't persist workspace/provider/effort across reloads

Refresh the GUI page → workspace resets to `./fixtures/sample-run`, provider mode resets to DEMO MODE, effort selector resets to `lite`. All page state is React `useState` only; nothing in localStorage.

**Symptom for friends:** "I had it pointed at my project but I refreshed and now it's back on the demo." Confusing because the live run is still going in the background; the user has to re-enter the workspace path to see the Board update.

**Fix:** persist `repoPath` + `providerMode` + `composerEffort` to `localStorage` and rehydrate on mount.

### #5 GUI's stale run-registry survives backend-state deletion

After `rm -rf .code-oz/state/`, the GUI's "Run History" sidebar still showed the old run as "IN PROGRESS" because the server-side run-registry caches the handle. A page refresh didn't fix it (the registry is per-server-process state). Required a server restart to clear.

**Symptom for friends:** "I see a ghost run in the sidebar that doesn't exist on disk."

**Fix:** the registry should validate against disk on read, or expose an `expire-stale` API the GUI can call.
