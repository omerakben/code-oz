# v0.21.1-alpha.0 — external-operator driving

Released 2026-05-22.

## What's new

An external autonomous agent (Hermes, OpenClaw, or any agent-first tool) can drive
the `code-oz` CLI as a tool, with a fail-closed operator mode that keeps code-oz the
gate authority.

Three ways to bind a run to an external operator, in increasing robustness:

1. Per-command flags — `code-oz run --operator <id> --non-interactive`
2. Session env var — `export CODE_OZ_OPERATOR=<id>`
3. Project binding — `code-oz init --operator <id>` writes `operator:` to
   `.code-oz/config.yaml`; every run/approve in that project is then operator-bound
   automatically, with no per-command action.

In any of those, the engine fails closed: it bans the fake provider (so cross-family
REVIEW cannot be stubbed), blocks SHIP approval (human-only), requires an explicit
phase for non-interactive approve, and records operator provenance
(`run_started.operator`, gate `approvedBy: operator:<id>`) while keeping
`actor: orchestrator`. A malformed operator id from any source fails closed.

A text-only agentskills.io skill ships at `agent-skills/code-oz/` for installing into
Hermes/OpenClaw skill directories. It carries no executable, drives the CLI directly,
and encodes the boundaries (never write `.code-oz/`, never decide pass/fail, never
simulate review, never use fake/push).

## Authority boundary

This release introduces one new authority boundary (rule 20): external-operator
driving authority — who may drive the existing gate machine non-interactively, and how
that is recorded. No new gate, no new provider. SWE-bench remains the v0.22 milestone.

## Scope notes

Deferred (documented, not in this release): MCP server surface, cross-run spend ledger,
per-operator quotas, config-hash assurance fingerprint, `--request-file`/`--artifact`
restrictions in operator mode. The operator-mode controls apply when a run is bound;
binding is the operator's setup step.
