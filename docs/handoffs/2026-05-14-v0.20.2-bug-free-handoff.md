## Showstopper #0a: BUILD prompt has no TASK_BLOCK injection

### What's broken

`src/prompts/build-system.md` template has 5 substitution slots: `{{UNIVERSAL_RULES}}`, `{{AGENT_BODY}}`, `{{COMMON_RATIONALIZATIONS}}`, `{{AVAILABLE_TOOLS}}`, `{{READY_SIGNAL}}`. There is **no slot for per-task PLAN.md content** (Files, Validation, Risk, Hypotheses from the T-NNN task block).

`src/prompts/index.ts:316` (`composeBuildPromptPure`) and `:337` (`composeBuildPrompt`) accept `agentBody` + `readySignal` + `availableTools` only. The PLAN task content is loaded by `src/phases/build.ts:362` (`loadPlanAndSelectTask`) **for the orchestrator's own use** (validation command, planSha) but never threaded into the prompt going to Opus.

### Proof

`build-attempt-1.prompt.txt` from run `01KRKW0D94C3F80002CSAR29NT`: 252 lines, contains no `prdiff`, no `Scaffold`, no `src/version.ts`, no `T-001` outside of an example placeholder ("A PLAN task `T-001` says 'implement two-syllable surname stress rule…'") that is the persona-prompt example, not the actual prdiff task. The agent_invoked event for the builder shows `filesSent: 0, bytesSent: 0`. Builder Opus correctly refused per rule 1 + rule 8 ("no claims you haven't verified," "no unstated assumptions"), emitting `NEEDS_INTERVENTION.json` with code `build_persona_protocol_violation`. Same failure on three separate retries (v0.20.0 binary AND v0.20.1 dev source).

### Fix sequence (TDD per rule 22)

1. **RED test first** at `tests/prompts/compose-build-prompt.test.ts`: assert that `composeBuildPromptPure({ ..., task: <PlanTask> })` produces a string containing the task's `id`, every entry in `task.files`, the verbatim `task.validation`, and the verbatim `task.risk`. Run it; confirm it fails for the right reason (composeBuildPromptPure doesn't accept a `task` parameter today).

2. **Edit `src/prompts/build-system.md`:** add a new section `## Task` with the substitution token `{{TASK_BLOCK}}` after the agent-body section, before the rationalizations.

3. **Edit `src/prompts/index.ts`:**
   - Add `const TOKEN_TASK_BLOCK = '{{TASK_BLOCK}}'`.
   - Add it to `BUILD_REQUIRED_TOKENS`.
   - Add `task: PlanTask` to `ComposeBuildPromptPureInput` and `ComposeBuildPromptInput`.
   - Render the task block with id, files, validation, risk, hypotheses, sources in a stable Markdown shape; replace `TOKEN_TASK_BLOCK` with the rendered string.

4. **Edit `src/phases/build.ts:423`:** pass `task: planLoad.task` into `composeBuildPrompt(...)`.

5. **Run all existing prompts/build-related tests** — confirm none regress.

6. **Rerun prdiff BUILD** on the paused run `01KRKW0D94C3F80002CSAR29NT` and assert builder Opus emits `<build-ready/>` + a unified-diff patch for T-001. This is the "dogfood passes" gate. If it doesn't, the fix isn't done.

### Acceptance criterion

## Showstopper #0b: Claude CLI subprocess has no tool-use loop wired in BUILD

### What's broken

`src/providers/claude.ts:65` invokes Claude CLI with `args = ['--print', '--output-format', 'json', '--no-session-persistence']`. This is single-shot mode: Claude reads a prompt, prints a JSON-wrapped response, exits. No tool-use loop. The builder Opus receives a prompt that says "You have `tool_use.repo_context` (`glob`, `grep`, `read`) bound to the run's worktree. Use them to verify file contents BEFORE crafting the patch" — but the orchestrator-to-CLI protocol layer never actually exposes those tools as callable.

`src/providers/invoke.ts` has a *receiving-end* handler for `stopReason: 'tool_use'` and `toolCalls`, with a code comment: "M7 BUILD/REVIEW orchestration will use this shape; M5 DEFINE never does (text-only)." Present tense "will use" — architected, not implemented.

`src/tools/repo-context/` IS fully implemented (`runner.ts`, `glob.ts`, `grep.ts`, `permissions.ts`). The runtime exists. The wiring from "builder emits tool_use block" → "orchestrator runs runRepoContextTool" → "orchestrator feeds tool_result back into Claude subprocess for next turn" does NOT exist.

### Proof

Across three BUILD attempts against the prdiff intent, the events.jsonl contains **zero `repo_context_searched` events** (the event runner.ts emits when execGrep/execGlob runs). Builder Opus's draft responses say "no PLAN.md in this empty directory" — meaning Opus never even attempted to glob/read the worktree because it had no callable tools to do so.

### Fix sequence (TDD per rule 22)

1. **RED test first** at `tests/providers/claude-tool-use-loop.test.ts` (new file): write a unit test that drives the Claude provider with a mocked CLI that returns a `tool_use` block on turn 0, asserts the test runner invokes `runRepoContextTool` with the right args, returns a synthetic `tool_result`, then makes a second CLI invocation that includes the prior `tool_use` + `tool_result` in the conversation. Assert the final response is captured. Confirm test fails today.

2. **Decide Claude CLI input shape.** Verify that `claude --print --output-format json` accepts a multi-turn conversation as JSON on stdin (Anthropic API tool-use shape). If yes, code-oz can emit each turn as a JSON conversation. If no, the protocol layer needs to use a different Claude CLI mode (`--continue` with a session ID, OR direct Anthropic SDK fallback when tool_use is requested).

3. **Implement the loop in `src/providers/claude.ts`:** when invocation receives a `tool_use` block in the response, the provider does not return to the caller; instead it loops:
   - Match each tool call against the agent's `permissions.tool_use.repo_context` (using `src/tools/repo-context/permissions.ts`).
   - Run `runRepoContextTool` for each call; append `repo_context_searched` events.
   - Append the `tool_use` + `tool_result` pair to the conversation.
   - Re-invoke Claude CLI with the extended conversation.
   - Repeat until response has no `tool_use`, or until `maxToolCallsPerTurn` (already in config) is hit.

4. **Hook orchestration in `src/providers/invoke.ts`** so the BUILD phase calls into this multi-turn path automatically when the persona has `tool_use.repo_context` permissions.

5. **Rerun prdiff BUILD T-001** with #0a + #0b both fixed. Confirm the events.jsonl contains at least one `repo_context_searched` event before the `agent_completed`. Confirm the patch lands in the worktree.

### Acceptance criterion

The `tests/providers/claude-tool-use-loop.test.ts` test passes. **Additionally**, the dogfood smoke (below) advances BUILD T-001 to `task_completed` with at least one `repo_context_searched` event in the run's events.jsonl. **Additionally**, the same loop works for REVIEW (cross-family GPT-5.5) — the loop must be provider-agnostic in `invoke.ts`.

## The dogfood smoke (mandatory pre-tag, every release going forward)

Add `scripts/release/dogfood-smoke.sh` (new). Behavior:

1. `mktemp -d` → `$TMP/dogfood-project`
2. `cd $TMP/dogfood-project && git init -q`
3. `<binary-under-test> init`
4. Write a synthetic SPEC seed to `INTENT.md` covering a small, deterministic CLI (e.g., "build a counter program in TypeScript that increments a value, prints, supports --reset; ship with offline tests").
5. `<binary-under-test> run --request "$(cat INTENT.md)" --effort lite`
6. `<binary-under-test> approve define`
7. `<binary-under-test> run` → wait for PLAN gate
8. `<binary-under-test> approve plan`
9. `<binary-under-test> run` → wait for BUILD task complete (no NEEDS_INTERVENTION)
10. Assert `events.jsonl` contains at least one `repo_context_searched` event (proves tool-use loop fires).
11. `<binary-under-test> approve build` → drive through VERIFY → REVIEW → SHIP.
12. Final assertion: a runnable artifact exists at the expected path.

Exit non-zero if any step fails. **Block the v0.20.2 tag on this script returning 0.**

Cost per run: ~$0.50-2 in real-provider tokens. Acceptable as the gate.
