### F9.2 - Drawer focus trap only tracks buttons, so textareas and other focusable controls can escape the modal cycle

- **Severity:** block-ship
- **Where:** `code-oz-gui/components/Drawer.tsx:64`, `code-oz-gui/components/AIHelper.tsx:159`, `code-oz-gui/components/DecisionsView.tsx:767`, `code-oz-gui/components/DecisionsView.tsx:919`
- **Evidence:**
  ```text
  Drawer focus trap:
  code-oz-gui/components/Drawer.tsx:64-66
    drawerRef.current.querySelectorAll<HTMLButtonElement>('button:not([disabled])')

  Focusable controls inside the drawer that are not buttons:
  code-oz-gui/components/AIHelper.tsx:159-165
    <textarea ... placeholder="Ask anything about this view..." ... />
  code-oz-gui/components/DecisionsView.tsx:767-773
    <textarea ... placeholder="What should the AI revise? Be specific." ... />
  code-oz-gui/components/DecisionsView.tsx:919-925
    <textarea ... placeholder="Your answer (optional, helps the AI proceed faster)" ... />
  ```
- **Why it matters for first-run UX:** Keyboard and screen-reader users can interact with text fields inside the modal, but the trap does not include those controls, so Tab order can become inconsistent or leave the dialog while `aria-modal="true"` says focus is contained.
- **Proposed fix:** Replace the button-only selector with a standard focusable selector covering `a[href]`, `button`, `textarea`, `input`, `select`, `[tabindex]:not([tabindex="-1"])`, and `[contenteditable="true"]`, then filter disabled and hidden elements. Store the opener before moving focus into the drawer and restore focus on close. RED-first sketch: add a Playwright test that opens the drawer, expands AI helper, focuses its textarea, presses Tab and Shift+Tab repeatedly, and asserts `document.activeElement` remains inside `role=dialog`; run it first to reproduce the escape or broken cycle, then fix.
- **Effort estimate:** s
