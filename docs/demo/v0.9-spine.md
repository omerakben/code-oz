# v0.9 spine demo — DEFINE → PLAN → BUILD → VERIFY → REVIEW

This walkthrough shows the full v0.9 spine end-to-end against the
`tests/fixtures/greenfield-baby-name` fixture. It mirrors the assertions
in `tests/e2e/review-lite-greenfield-pass.test.ts` (single-round) and
`tests/e2e/review-lite-greenfield-multi-round.test.ts` (multi-round) so
human reviewers can follow the artifacts as they are produced.

## Prerequisites

- `git >= 2.40` on `PATH` (worktree-per-run isolation).
- `bun >= 1.3` (project's pinned runtime).
- A clean checkout of `code-oz` at the v0.9 tag.
- No active run (`.code-oz/state/active.json` absent or referencing a
  closed run).

## Walkthrough

The fixture lives at `tests/fixtures/greenfield-baby-name/`. It carries
a tiny TypeScript surface (`src/candidates.ts` with a `topN` helper and
its `tests/candidate-select.test.ts`). The single-round flow lands a
docstring change against `topN`; the multi-round flow has the reviewer
ask for the docstring to mention the stable-on-ties property
explicitly, then the second-attempt patch addresses the finding.

### 1. DEFINE → SPEC.md

Drives the BA persona via FakeProvider. The BA emits `<spec-ready/>`
followed by the canonical SPEC.md body. `runDefine` writes
`.code-oz/artifacts/SPEC.md` atomically and emits `gate_required(define)`.

```
$ code-oz approve define
```

Advances the FSM to `plan`.

### 2. PLAN → PLAN.md + SOURCE_CHECK.md

Drives the Lead persona via FakeProvider. The Lead emits both
`# PLAN` and `# SOURCE_CHECK` blocks; `runPlan` parses them into the
two artifacts. The Scientist phase-tail follows, producing
`HYPOTHESES.md` and `OPEN_QUESTIONS.md`.

Gate-preflight (CLAUDE.md rule 15) runs after the Scientist tail and
before `requireGate(plan)` to block on overdue / blocking open
questions. The fixture's `Q-001` is `Importance: low` with `DueBy:
2026-12-31`, so preflight passes.

```
$ code-oz approve plan
```

Advances to `build`.

### 3. Worktree creation (M7 substrate)

`createRunWorktree({ cwd, runId })` creates `.code-oz/runs/<runId>/worktree/`
as a git worktree off the project root's HEAD. The worktree survives
through BUILD, VERIFY, and REVIEW; cleanup happens at `code-oz approve
review` (M9 commit 1 substrate; the cleanup hook moved off VERIFY-approve
in M9 to satisfy REVIEW's read-the-changed-files requirement).

### 4. BUILD → BUILD_REPORT.md

`runBuild` invokes the Builder persona via the `invokePersona` shim;
the persona returns a `<build-ready/>` token, a unified-diff patch
block, and a `## Title` + `## Notes` block. The orchestrator applies
the patch to the worktree, computes the changed-file manifest, and
writes the canonical BUILD_REPORT.md.

A separate `build_provider_recorded` event (M9 commit 1 substrate) is
emitted immediately after `build_completed`. It records the Builder
agent's resolved provider id + family + model — REVIEW's
invocation-time cross-family check reads this event durably without
re-deriving the BUILD adapter's family.

```
$ code-oz approve build
```

Advances to `verify`.

### 5. VERIFY → VERIFY.md

`runVerify` runs the validation command from BUILD_REPORT.md against
the worktree, captures evidence (exit code, duration, stdout/stderr
bytes + log paths), evaluates the mutation gate, and computes the
binary verdict. The Verifier persona authors only `## Rationale` (and
`## Failure summary` + `## Constraint` on fail).

The Scientist phase-tail runs on both pass and fail branches; the
gate-preflight then runs and `requireGate(verify)` fires on success.

```
$ code-oz approve verify
```

Advances to `review`. Worktree survives (M9 commit 1 substrate).

### 6. REVIEW round 1 → REVIEW.md

`runReview` is the M9 commit 7 orchestrator. Sequence:

1. Reads BUILD_REPORT.md + VERIFY.md (verdict must be `pass`).
2. Cross-family invocation-time check: latest `build_provider_recorded`
   family vs `familyOf(reviewerAgent.provider)`. The fixture uses
   `claude` for BUILD and `codex` for the Reviewer; they differ, so the
   check passes.
3. Renders `{{REVIEW_CONTEXT}}` (round number, upstream refs,
   changed-file manifest, VERIFY pass summary, prior round digests).
4. Emits `review_started` with the cross-family pair recorded.
5. Invokes the Reviewer persona for `## Findings` + `## Score`. Two
   drafts max; rejected drafts persist under
   `.code-oz/runs/<runId>/review-drafts/round-N-attempt-M.md`.
6. Canonicalizes findings (fingerprint reuse + ping-pong reopen).
7. Computes the orchestrator-owned verdict.
8. Round-trip serializes → parses REVIEW.md for grammar lock-in.
9. Atomic-writes REVIEW.md.
10. Emits `review_round_completed`.
11. On `verdict: ready`: emits `review_resolved`, runs Scientist tail,
    runs gate-preflight, fires `requireGate(review)`. On `verdict:
    block`: emits `review_blocked(reason='block')` + writes
    `NEEDS_INTERVENTION.json` with code `review_block_terminal`. On
    `verdict: needs-revision`: hands off to the M9 commit 10 remediation
    coordinator.

```
$ code-oz approve review
```

`preApproveReviewHook` (M9 commit 1) reads the latest
`build_provider_recorded` event, removes the worktree via `git
worktree remove --force`, emits `worktree_destroyed (phase=review)`,
then `approveGate` writes `GATE_REVIEW_PASSED.json` and the FSM
advances to `ship`.

### 7. Multi-round path (T-003-flavored)

When round 1 exits with `verdict: needs-revision`, the M9 commit 10
remediation coordinator decides:

- **REVIEW cap** (rounds 1..4 used): `review_cap_exhausted` → emits
  `review_blocked(reason='cap_exhausted')` and writes
  `NEEDS_INTERVENTION.json` with code
  `review_cap_exhausted_terminal`. Reopened ids (ping-pong detection,
  decision 2) are named explicitly when present.
- **BUILD cap** (clean BUILD attempts at 4): `build_cap_blocked` →
  VERIFY-owned intervention with `while addressing REVIEW round N`
  context. `review_blocked` is NOT emitted in this path (decision 4
  authority overlap).
- **Continue**: produces a typed carry-forward block (`Source:
  review-needs-revision`, M9 commit 9 substrate) and returns it on the
  `ReviewNeedsRevision.carryForward` field. The caller (run loop)
  schedules BUILD attempt N+1 with the carry-forward, then VERIFY,
  then REVIEW round N+1.

The round-2 REVIEW.md timeline carries both rounds (contiguous from 1).
Findings raised in round 1 are marked `Round resolved: 2` in the round-2
canonical artifact when the persona claims them resolved; ids that
fingerprint-match a prior-resolved finding get reopened with the
original F-NNN id (no new id is minted for re-occurrence).

## What to inspect

After a successful run, the artifact tree under
`.code-oz/artifacts/`:

```
SPEC.md           # DEFINE
PLAN.md           # PLAN
SOURCE_CHECK.md   # PLAN
HYPOTHESES.md     # Scientist sidecar (last writer wins; updated each phase)
OPEN_QUESTIONS.md # Scientist sidecar
BUILD_REPORT.md   # BUILD (last attempt's report)
VERIFY.md         # VERIFY (last attempt's report)
REVIEW.md         # REVIEW (last round's canonical report)
```

Run state under `.code-oz/state/runs/<runId>/`:

```
events.jsonl              # append-only audit trail
current.json              # derived FSM state (regenerated on every event)
GATE_DEFINE_PASSED.json
GATE_PLAN_PASSED.json
GATE_BUILD_PASSED.json
GATE_VERIFY_PASSED.json
GATE_REVIEW_PASSED.json
review-drafts/            # ignored persona drafts (cleaned post-canonical-write)
forensics/<attempt>/      # VERIFY-fail forensics bundles (when present)
```

Cross-family proof (the M9 product surface) is recorded twice:

1. In `events.jsonl` — `review_started` carries `buildFamily` and
   `reviewerFamily` fields explicitly.
2. In `REVIEW.md` — `## Reviewer` block has `Cross-family check:
   passed (BUILD family: <fam>; reviewer family: <fam>)`.

Both must agree; the parser validates the REVIEW.md form, the events
schema validates the event form, and the M9 commit 1 family-aware
loader closes the load-time hole.
